NeyroMusic

Система разделения музыки на инструментальные дорожки

О себе и процессе работы

Я работала над подобным проектом впервые, многие темы для меня были новыми. При создании использовала информацию из интернета, документацию библиотек, статьи, а также обращалась за помощью к нейросети, которая помогала разбираться в сложных моментах, структурировать код и выполняла рутинную работу. Весь процесс занял примерно 16 часов чистого времени, растянутых примерно на два дня.

Что именно было реализовано

1. Выбор модели для разделения

Была выбрана модель Hybrid Demucs от Facebook Research. Информацию о ней нашла в интернете. Эта модель считается одной из лучших для отделения вокала и инструментов. Она выдает 4 стема: вокал, барабаны, бас и всё остальное. Модель загружается через библиотеку torchaudio, что оказалось очень удобно.

2. Обработка одного трека через скрипт separator.py

Был создан скрипт separator.py, который можно запускать из командной строки. Он умеет:

- Загружать аудио в форматах MP3, WAV, FLAC, M4A, MP4
- Обрезать тишину в начале и конце (ускоряет обработку)
- Разбивать длинные треки на чанки и склеивать обратно
- Кэшировать результаты, чтобы не обрабатывать тот же файл дважды

Как запустить:

```
python separator.py "путь к файлу.mp3"
```

Пример с файлом из MUSDB18:

```
python separator.py "musdb18/test/Arise - Run Run Run.stem.mp4"
```

Дополнительные возможности:

```
python separator.py "путь к файлу.mp3" -o my_output --no-cache --no-trim -d cpu
```

Где:
- -o папка для сохранения результатов
- --no-cache отключает кэширование
- --no-trim отключает обрезку тишины
- -d выбор устройства (cuda или cpu)

Важный момент: если в названии файла есть пробелы, нужно брать его в кавычки. Например:

```
python separator.py "C:\Мои песни\мой трек.mp3"
```

Без кавычек командная строка решит, что это несколько разных аргументов, и выдаст ошибку.

3. Оценка качества на MUSDB18

Характеристики моего компьютера, на котором проводилось тестирование:
- Процессор: AMD Ryzen 5 5600GT 3.60 GHz
- Оперативная память: 16 ГБ
- Видеокарта: AMD Radeon Graphics (встроенная, 496 МБ)
- CUDA (NVIDIA): нет, поэтому код работал на CPU

Для оценки качества был написан скрипт evaluate_musdb.py. Он берет треки из папки musdb18 (было использовано 5 треков в демонстрационных целях), запускает разделение и считает метрики SDR, SIR, SAR для каждого стема. Расчёт метрик был написан вручную на основе формул из статей про оценку аудиоразделения.

Как запустить оценку:

```
python evaluate_musdb.py --musdb-path musdb18 --max-tracks 5
```

Результаты оценки для 5 треков:

- Вокал: средний SDR = 15.28 дБ (отлично)
- Барабаны: средний SDR = 4.64 дБ (средне)
- Бас: средний SDR = 5.76 дБ (средне)
- Остальное: средний SDR = 4.64 дБ (средне)

Модель лучше всего справляется с вокалом. С барабанами и остальными инструментами бывают сложности — это известная проблема Demucs, так как барабаны часто перекрываются по частотам с другими инструментами.

Был создан график evaluation_plot.png, где визуально показаны все три метрики для каждого стема. Также сохранена таблица evaluation_results.csv с детальными показателями по каждому треку.

4. REST API и веб-интерфейс

Был разработан веб-сервер на FastAPI. Основной эндпоинт работает по адресу /separate, принимает аудиофайл через форму и возвращает ZIP-архив с четырьмя WAV-файлами.

Чтобы запустить сервер:

```
python app.py
```

После этого сервер доступен по адресу http://localhost:8000

Также был создан простой веб-интерфейс, который открывается по тому же адресу. Там можно выбрать файл, загрузить его и скачать готовые дорожки.

5. Оптимизации обработки

Было реализовано несколько оптимизаций:

- Обрезка тишины — перед обработкой система вырезает тишину в начале и конце трека. Это ускоряет работу. В одном из тестовых треков было обрезано почти 60 секунд тишины. В примере с separator.py обрезано 2.9 секунды.

- Разделение на чанки — для длинных треков система режет аудио на куски по 10 секунд с перекрытием 1 секунду, обрабатывает каждый кусок отдельно, а потом склеивает обратно. Это позволяет не перегружать память на компьютере с 16 ГБ ОЗУ. В скриншоте видно, что трек длиной 210 секунд был разбит на 25 чанков.

- Кэширование — каждый файл получает уникальный хеш, и если этот же файл загружается повторно, система возвращает уже готовые стемы из кэша, не тратя время на повторную обработку.

- Поддержка GPU — код автоматически определяет, есть ли видеокарта NVIDIA с CUDA, и использует её для ускорения. На моём компьютере видеокарта AMD, поэтому CUDA не доступен, и код работал на процессоре (вывелось сообщение "CUDA не доступен, использую CPU").

Как всё запустить и проверить

Шаг 1. Установить библиотеки

Все зависимости описаны в файле requirements.txt. Установка выполняется командой:

```
pip install -r requirements.txt
```

Важный момент: при первом запуске любой команды, использующей разделение, произойдёт автоматическая загрузка весов модели. Это займёт несколько минут, так как модель весит около 300 МБ.

Шаг 2. Проверить, что всё работает, через separator.py

```
python separator.py "путь к вашему файлу.mp3"
```

Результаты появятся в папке output.

Шаг 3. Запустить веб-сервер с интерфейсом

```
python app.py
```

Затем открыть в браузере http://localhost:8000

После этого перетащить файл, дождаться обработки и сохранить ZIP-архив. В нём будут четыре WAV-файла с разделёнными дорожками.

Шаг 4. Оценить качество на датасете MUSDB18

```
python evaluate_musdb.py --musdb-path /путь/к/musdb18 --max-tracks 5
```

Тонкости и важные моменты

1. Пробелы в именах файлов. Если путь к файлу содержит пробелы, обязательно заключайте его в кавычки. Иначе командная строка разобьёт название на несколько частей.

2. Первый запуск медленный. Модель скачивается только один раз. После того как веса сохранены на диск, следующие запуски будут быстрее.

3. MP4 файлы работают, но через pydub. Librosa не всегда справляется с MP4, поэтому код автоматически переключается на pydub. В консоли может появиться предупреждение "PySoundFile failed. Trying audioread instead" — это нормально, обработка продолжится.

4. RTF (Real Time Factor). Показывает, во сколько раз обработка быстрее или медленнее реального времени. Значение 0.27 означает, что на обработку одной секунды аудио уходит 0.27 секунды, то есть система работает быстрее, чем длится песня.

5. Кэш хранится в папке cache. Если нужно освободить место, можно удалить эту папку. При следующем запуске кэш создастся заново.

6. Если на компьютере есть видеокарта NVIDIA с CUDA, код автоматически её использует. Скорость обработки вырастет в несколько раз. На AMD видеокартах ускорение через CUDA не работает.

Что не успела или не сделала

Из дополнительных пунктов не была реализована контейнеризация с Docker. Также не создавала отдельный Jupyter notebook.

Основные проблемы и узкие места

1. Производительность на CPU. Модель Demucs довольно тяжёлая, на процессоре трёхминутный трек обрабатывается около 50-60 секунд. RTF составляет около 0.27. На GPU результат был бы значительно лучше, но видеокарта AMD не поддерживает CUDA.

2. Качество разделения барабанов. Судя по метрикам, drums и other показывают результаты хуже, чем вокал и бас. Из информации в интернете это известная проблема Demucs, так как барабаны часто перекрываются по частотам с другими инструментами.

3. Ограничение по длительности. В API установлено ограничение в 10 минут, в основном из-за ограниченной оперативной памяти (16 ГБ). При большем размере файл может не влезть в память.

4. Librosa и MP4. При загрузке MP4 файлов через librosa появляются предупреждения, но обработка не останавливается — код переключается на pydub.
